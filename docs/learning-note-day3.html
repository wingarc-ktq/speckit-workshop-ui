SECTION 03「なぜ？」で理解する仕組み

ここからは、今日の作業で下した判断を「なぜそうしたのか」から説明します。答えを知るより、理由を知るほうが応用が利きます。

?なぜ AI にわざわざ画面を「見せる」必要があったのか

コードを読むだけでは、実行して初めて決まることが分からないから。

Claude はリポジトリのソースコードを全部読めます。それなら画面を見なくてもテストが書けそうに思えます。でも実際には書けません。

たとえるなら、レシピを読んだだけで「盛り付けた皿の写真」は描けないのと同じです。材料と手順は分かっても、最終的にどう見えるかは作ってみないと分かりません。

コードから分かること実際に見ないと分からないこと
<DataGrid> を使っている そのDataGridが実際に吐き出すHTMLの構造（data-rowindex という属性が付くこと）
検索フィールドがある 入力から300ms後に検索が走ること
ルーティングの定義 ログイン後に実際に飛ぶURLが / であること
ページネーションの実装 1ページの既定が10件で、"1–5 of 7" という形式で表示されること

Playwright MCP は、この右側の列を Claude に見せるための道具です。MCP がないと、Claude は左側の情報から右側を「推測」して書きます。推測なので当たりません。

実際に効いた場面

資料には「http://localhost:5173/files のファイル一覧画面」と書いてありました。もし資料を信じて書いていたら、存在しないURLにアクセスして全テストが落ちていました。MCP で実際に開いたから、正しいURLが / だと分かったのです。

?なぜ先に日本語の仕様書を書いたのか

コードから書き始めると、「動いたからOK」に流れて、何を保証しているのか誰も説明できなくなるから。

テストコードをいきなり書くと、こういうことが起きます。「このテスト、何を確かめてるんだっけ？」「なんとなく通ってるから触らないでおこう」。テストがブラックボックスになってしまう。

先に日本語で「何をどう操作したら、何が起きるべきか」を書いておくと、こうなります。

仕様書の見出しテストコード
## 〜すること → test('〜すること', ...)
### 前提条件 → beforeEach()
### 手順 → テスト本体
### 事後処理 → afterEach()

プログラムが読めない人でも、仕様書を見ればテスト内容が分かる。これが「マークダウン仕様書駆動」の目的です。テストは開発者だけのものではなく、チーム全体で「何を保証しているか」を共有するためのものだからです。

?なぜ操作を Page Object に分けたのか

画面が変わったときに、直す場所を1箇所に閉じ込めるため。

テレビのリモコンを想像してください。私たちは「音量+」ボタンしか知りませんが、それで操作できます。もしリモコンがなく、毎回テレビの裏蓋を開けて配線を触れと言われたら大変です。

Page Object はこのリモコンにあたります。

// ❌ Page Object を使わない場合 — 6つのテストすべてにこう書く
await page.getByTestId('searchField').fill('田中商事');
await page.waitForTimeout(350);

// ⭕ Page Object を使う場合 — 意図だけを書く
await fileListPage.search('田中商事');

いま検索ボックスの data-testid が変わったとします。

  • 使わない場合：6つのテストファイルを全部開いて、6箇所直す
  • 使う場合：FileListPage.ts の search() の中を1箇所直すだけ。テストコードは無変更

今日の時点では手間が増えたように見えます。クラスを作る作業が増えただけですから。効いてくるのは、画面が変わったとき・テストが増えたときです。テストが3つを超えたあたりから確実に元が取れます。

?なぜ表示されている文字ではなく data-testid で要素を探すのか

見た目は変わるけれど、テスト用の目印は変わらないから。

スーパーのレジは、商品のパッケージデザインが変わっても正しく会計できます。見た目ではなくバーコードを読んでいるからです。

このアプリは日本語と英語を切り替えられます。つまり「ファイルを検索...」という文字は、いつでも "Search files..." に変わりうる。文字で探すテストは、その瞬間に全部落ちます。

探し方壊れる条件評価
getByTestId('searchField') 開発者が意図的に消したときだけ ◎ 最も安全
getByRole('button', {name:'Go to next page'}) MUIライブラリの仕様が変わったとき ○ かなり安全
[role="row"][data-rowindex] MUIの公開仕様が変わったとき ○ 安全
.MuiDataGrid-row（CSSクラス） MUIのバージョンアップ △ 危険
getByText('検索結果が見つかりませんでした') 言語切替・文言修正 ✕ すぐ壊れる
なぜ本体のコードを書き換えてよかったのか

検索ボックスには目印がなかったので、AppHeader.tsx に data-testid="searchField" を追加しました。「テストのために製品コードを変えるのは邪道では？」と思うかもしれませんが、プロジェクト憲法に「E2Eテストの要素特定には data-testid を使用すること」と明記されています。目印がないほうが憲法違反だったわけです。

?なぜ「待つ」処理がこんなに必要なのか

人間が目で見ている「一瞬」の裏で、4段階の処理が順番に起きているから。

ファイルをアップロードすると、人間には「ポンと一覧に出た」ように見えます。実際にはこうです。

  1. ブラウザがファイルを読み込む
  2. サーバー（今回はMSW）に送信する ← 通信
  3. 成功したので、一覧を取り直す ← また通信
  4. 受け取ったデータで表を描き直す ← 画面の更新

プログラムは人間より圧倒的に速いので、1が終わった瞬間に「一覧に2件あるはず」と確認しに行きます。当然まだ0件です。テストは失敗します。

これが最初にテストが全滅した理由でした。「操作した」と「結果が出た」は別の時刻に起きる。この感覚が E2E テストの核心です。

デバウンスという、もう一つの待ち

エレベーターの「閉」ボタンを連打しても、扉は連打の回数だけ動きません。最後に押されてから少し待って、一度だけ閉まります。

検索ボックスも同じ仕組みです。「田中商事」と打つと4回のキー入力が起きますが、毎回サーバーに問い合わせたら4回も無駄な通信が発生します。だから 「最後の入力から300ミリ秒待って、それから1回だけ検索する」。これがデバウンス。

この300msは仕様書のどこにも書かれていません。Playwright MCP で実際に触って初めて分かったことです。もし知らずにテストを書いていたら、「なぜか時々落ちる」という一番厄介なテストができあがっていました。

?なぜ expect.poll を使うのか — 固定時間待つのではダメなのか

待ち時間は環境によって変わるので、「決め打ちの時間」は必ずどこかで外れるから。

料理を注文したあと、確認方法は2つあります。

やり方問題
「たぶん10分」と決めて
10分後に取りに行く
＝ waitForTimeout		 早くできていたら待ち損（テストが遅くなる）。
遅れていたら空振り（テストが落ちる）。
混雑具合で変わるのに固定にしている時点で無理がある。
30秒おきに「できました?」と
聞きに行く（最大5分）
＝ expect.poll		 できた瞬間に受け取れるので速い。
遅れても最大5分は待つので落ちにくい。

だから Playwright 公式は waitForTimeout を非推奨としています。CI サーバーは開発PCより遅いことが多く、手元では通るのに CI では落ちる、という事態を招くからです。

ただし、今回あえて固定待機を1箇所だけ残した

デバウンスの300msは「必ず経過しなければ処理が始まらない時間」です。何度確認しに行っても、300ms経つまでは何も起きません。こういう場合は待つしかない。

その後の「画面に反映されるまで」は、いつ終わるか分からないので expect.poll に任せています。「非推奨だから全部やめる」ではなく、なぜ非推奨なのかを理解して使い分けるのが正しい姿勢です。

SECTION 04重要なコード — なぜそう書くのか

1. アップロードの完了を待つ

最初の版が全滅した原因の箇所です。なぜこの順番でなければいけないのかに注目してください。

playwright/tests/pages/FileListPage.ts 
async uploadFiles(filePaths: string[], expectedRowCount?: number) {
  for (const filePath of filePaths) {

    // ★なぜ「待つ約束」を先に作るのか★
    // 操作を先にやると、通信が一瞬で終わってしまい、
    // 待ち始めたときには既に過ぎ去っていて永久に待つことになる
    // → 「網を張ってから魚を追い込む」順番が必須
    const uploadResponse = this.page.waitForResponse(
      (response) =>
        response.request().method() === 'POST' &&      // アップロードのPOSTだけを対象に
        response.url().includes('/api/v1/files') &&
        response.ok()                                  // 失敗レスポンスを掴まないように
    );

    // なぜ1件ずつなのか：まとめて渡すと完了順が保証されず、
    // 「何番目のファイルの応答か」を特定できなくなる
    await this.page.getByTestId('dropInput').setInputFiles(filePath);

    await uploadResponse;   // ここで初めて送信完了を待つ
  }

  // ★なぜ通信を待つだけでは足りないのか★
  // 通信が終わっても、画面の表が書き換わるのはさらに後だから。
  // ブラウザ内でJSを繰り返し実行して、行数が期待どおりになるまで待つ
  if (expectedRowCount !== undefined) {
    await this.page.waitForFunction(
      (count) =>
        document.querySelectorAll('[role="row"][data-rowindex]').length === count,
      expectedRowCount
    );
  }
}

2. テスト用のダミーファイルを作る

全テストの前提が「ファイルがアップロード済みであること」。なぜ本物のPDFを用意しないのかがポイントです。

playwright/tests/fixtures/testFiles.ts 
// ★なぜ中身が空同然でいいのか★
// ブラウザは拡張子(.pdf)からMIMEタイプを判断してサーバーに送る。
// 今回テストしたいのは「一覧に出るか・検索で引っかかるか」であって
// PDFの中身ではない。だから最小限のバイト列で足りる
const MINIMAL_PDF_CONTENT = Buffer.from(
  '%PDF-1.4\n1 0 obj<<>>endobj\ntrailer<<>>\n%%EOF'
);

export function createTestFiles(fileNames: string[]): string[] {
  // ★なぜ固定のフォルダ名にしないのか★
  // mkdtempSync は末尾にランダム文字列を足したフォルダを作る
  //   例: /tmp/file-list-e2e-A3xK9p
  // テストを2並列で走らせても、互いのファイルを上書きしない
  const dir = fs.mkdtempSync(path.join(os.tmpdir(), 'file-list-e2e-'));

  return fileNames.map((fileName) => {
    const filePath = path.join(dir, fileName);
    fs.writeFileSync(filePath, MINIMAL_PDF_CONTENT);
    return filePath;   // 絶対パスを返す。setInputFiles がこれを受け取る
  });
}

3. テストの骨組み

仕様書の1ケースが、そのまま1つの describe になります。なぜケースごとに分けたのかを見てください。

playwright/tests/specs/files/file-list.spec.ts 
// ★なぜケースごとにdescribeを分けたのか★
// ケースによって必要なファイル数が違うから（2件・5件・7件）。
// 全部まとめて1つのbeforeEachにすると、2件で足りるテストにも
// 7件アップロードすることになり、無駄に遅くなる
test.describe('キーワード検索でファイル名が一致する文書のみ表示されること', () => {
  let fileListPage: FileListPage;
  let testFilePaths: string[];

  // 仕様書の【前提条件】に対応する部分
  test.beforeEach(async ({ page }) => {
    fileListPage = await loginAndOpenFileList(page);
    testFilePaths = createTestFiles(['田中商事_請求書.pdf', '佐藤建設_契約書.pdf']);
    // 第2引数 = 「2件表示されるまで待て」の指示
    await fileListPage.uploadFiles(testFilePaths, testFilePaths.length);
  });

  // 仕様書の【事後処理】に対応する部分
  test.afterEach(async ({ page }) => {
    cleanupTestFiles(testFilePaths);
    await page.reload();
  });

  // テスト名 = 仕様書の見出しをそのままコピー
  // → レポートを見た人が、仕様書のどこの話か即座に分かる
  test('キーワード検索でファイル名が一致する文書のみ表示されること', async () => {
    await fileListPage.fillSearch('田中商事');        // 仕様書の手順2
    await fileListPage.waitForSearchDebounce();     // 仕様書の手順3

    // ★なぜ expect ではなく expect.poll なのか★
    // 一度だけ確認する expect(...) だと、まだ画面が更新されていない
    // 一瞬を掴んでしまう可能性がある。pollなら1になるまで繰り返す
    await expect.poll(() => fileListPage.getFileRowCount()).toBe(1);

    expect(await fileListPage.isFileVisible('田中商事_請求書.pdf')).toBe(true);
    expect(await fileListPage.isFileVisible('佐藤建設_契約書.pdf')).toBe(false);
  });
});

SECTION 05今回の学び

気づきMCP の価値は「AIに現実を見せること」だった

MCP を使わずに Claude にテストを書かせていたら、こう書いていたはずです — 資料に書いてある /files にアクセスし、デバウンスを知らずに即座に検証し、存在しないグリッドビュー切替をテストする。全部落ちます。

教訓：AI が間違えるのは能力不足ではなく情報不足のことが多い。MCP は「AIに正しい情報を与える配管」であって、AIを賢くする道具ではありません。

気づきMCP とテスト実行ツールは別物

完成した file-list.spec.ts に MCP は一切登場しません。今後このテストを CI で回すときも MCP は不要です。MCP は開発中の足場で、テストが完成したら外れます。

教訓：「AIツールを使って作ったもの」と「AIツールがないと動かないもの」は違う。今日作ったのは前者です。

つまずき「操作した」と「結果が出た」は別の時刻

最初の版は setInputFiles の直後に行数を数えていて、全滅しました。人間には一瞬に見える裏で、通信2回と画面更新1回が順番に起きています。

教訓：E2Eテストが落ちたら、まず「早すぎないか」を疑う。書いた本人は正しいと思っているので、これがいちばん気づきにくい。

つまずき同じURLを別の用途でも叩いていた

「一覧の再取得を待つ」ために GET /api/v1/files を待つ実装にしたら、逆に不安定になりました。「最近使用したファイル」も同じエンドポイントを叩いていたため、関係ないほうの通信を掴んでいたのです。

教訓：URLだけでリクエストを特定できるとは限らない。特定できないときは、通信を待つのをやめて「画面の最終状態」を待つほうが確実です。手段にこだわらず目的（結果が反映されたこと）を見る。

つまずきソートが1ページ目にしか効かない

実装を読むと、ページ送りは paginationMode="server"（サーバー任せ）なのに、ソートは指定なし＝client（ブラウザ側）でした。つまり「いま取得済みの行」の中でしか並び替わりません。

教訓：E2Eテストは、テストを書く過程で実装の設計ミスを見つける道具でもある。今回はテスト側で回避しましたが、本来は実装を直すべき問題です。

気づき本番ビルドで消える目印がある

MUI のアイコンには data-testid="CloseIcon" が自動で付きます。便利そうですが、ライブラリのソースを読むと NODE_ENV !== 'production' の時だけ付ける実装でした。本番ビルドでは消えます。

教訓：「たまたま存在する属性」に頼らない。なぜそれが存在するのかを確認してから使う。

気づきafterEach のリロードは、実は不要だった

MSW のデータをリセットするため page.reload() を入れましたが、Playwright はテストごとに新しいブラウザコンテキストを作るので、そもそもデータは共有されていませんでした。

教訓：ツールが既にやってくれていることを、自分で書き足していないか。「念のため」の処理も、理由を説明できなければ削るべきです。

つまずきテストが全滅したが、原因はコードではなかった

pnpm test:e2e:chromium をそのまま実行すると、新規テストどころか既存のログインテストまで落ちました。原因は並列実行数。WSL環境で Chromium を何個も同時起動して、Vite dev サーバーが処理しきれていませんでした。

PLAYWRIGHT_WORKERS=2 pnpm test:e2e:chromium   # → 12/12 成功

教訓：「今まで通っていたテストまで落ちた」は環境を疑うサイン。自分が書いた部分だけが落ちたならコード、全体が落ちたなら環境。切り分けの基準になります。

気づき3日間の総括 — 判断は人、作業はAI

今日、Claude は11分かけて画面を調べ、25分かけてテストを書いては直しました。その間に自分がやったのは、テスト範囲を絞る / 生成物をレビューして4点の修正を指示する / 環境問題とコード問題を切り分けるという判断です。
