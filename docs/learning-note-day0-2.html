WingArc1st インターン / Day 0 – Day 2

仕様書からアプリを作る
Spec Kit ワークフロー

日本語で書いた「作りたいもの」から、動く React 画面までを AI と一緒に組み立てる。文書管理システムの MVP 実装まで。

SECTION 01概要

このワークショップで扱ったのは Spec Kit という開発の進め方です。「コードを書く」のではなく「何を作るかを日本語で正確に決める」ことに時間を使い、そこから設計・実装を AI に展開させます。

できるようになったこと

  • 仕様書（spec.md）を読み解き、優先度 P1 の「最低限これがないと意味がない機能」を切り出せる
  • /speckit.plan → /speckit.tasks → /speckit.implement という決まった順番で開発を進められる
  • OpenAPI という「API の設計図」から、TypeScript の型・通信コード・テスト用の偽サーバーを自動生成できる
  • Node.js / pnpm / MSW / Playwright が動く開発環境をゼロから構築できる

3日間の流れと、いまどこにいるか

Day 0 ─ 全体像を掴む Spec Kit とは何か。7つのコマンドの役割。プロジェクト憲法という「守るべきルール」の存在。
▼
Day 1 ─ デザインと計画（Spec → Plan） spec.md を読んで画面を洗い出し、Figma でデザイン。/speckit.plan で技術的な実装計画 plan.md を作る。
▼
Day 2 ─ 実装（Plan → Code） /speckit.tasks で 100 個以上の作業に分解し、/speckit.implement で React コンポーネントを生成。文書一覧・検索・アップロードが動く状態に。
▼
Day 3 ─ テスト（← いまここ） Playwright でブラウザを自動操作する E2E テストを書く。
Day 2 までの成果物

ログインすると開く「マイファイル」画面。ファイル一覧テーブル（名前・タグ・更新日時・サイズ）、キーワード検索、ドラッグ&ドロップのアップロードエリア、ページネーション、タグ表示。約 130 個のタスクの積み重ねです。

SECTION 02直感的な補足 — レストランの厨房にたとえる

Spec Kit の登場人物は多くて混乱しがちです。ぜんぶ「レストランで料理を出すまで」に置き換えると、役割がはっきりします。

🍴Spec Kit ＝ 注文から配膳までの流れ

お客さんが「こういう料理が食べたい」と言ってから、実際に皿が出てくるまで。厨房ではこういう順番で進みます。

レストランではSpec Kit では
お客様の注文書
「魚料理で、あっさりめで」		 → spec.md（仕様書）
日本語で書かれた「作りたいもの」。ここが全ての出発点。
店のハウスルール
「うちは必ず国産食材」「化学調味料は使わない」		 → constitution.md（プロジェクト憲法）
TypeScript は strict、UI は Material-UI、テストなしはマージ禁止。例外なし。
料理長の調理計画
「蒸し器を使う。ソースは先に仕込む」		 → plan.md（実装計画）
どのライブラリを使い、どういう構成で作るかの技術判断。
作業手順書
「①野菜を切る ②鍋を火にかける…」		 → tasks.md（タスク一覧）
130 個の粒度まで分解。同時にやれる作業には印がつく。
実際の調理 → /speckit.implement
手順書どおりにコードを書いていく工程。

ポイントは順番を飛ばせないこと。 注文書がないのに調理を始めたら、何を作っているのか誰にも分かりません。Spec Kit が「まず仕様書」と言い張るのはこのためです。

✂OpenAPI と Orval ＝ 型紙と裁断機

洋服工場を想像してください。型紙が1枚あれば、そこから同じサイズの服を何着でも作れます。手で測って切ると、どうしても1枚ごとに微妙にズレます。

型紙 → schema/files/openapi.yaml — 「サーバーとやりとりするデータの形」を1箇所に書いた設計図
裁断機 → pnpm gen:api（Orval）— 型紙を読んで、TypeScript の型・通信コード・偽サーバーを自動で吐き出す
できあがった服 → src/adapters/generated/files.ts — 手書き禁止。型紙を直して裁断機を回し直す

だから API の仕様を変えたいときは、生成されたコードではなく型紙（yaml）を直す。生成物を手で書き換えると、次に裁断機を回した瞬間に消えます。

🍣MSW ＝ ショーケースの食品サンプル

飲食店の店頭にある、あのロウでできた food サンプル。本物の厨房が動いていなくても、見た目の確認はできる。これが MSW（Mock Service Worker）です。

今回のワークショップにはサーバー（バックエンド）が存在しません。それでも画面にファイル一覧が出るのは、MSW がブラウザの中で「サーバーのふり」をして、それっぽいデータを返しているからです。

食品サンプルなので、片付けると消える

MSW のデータはブラウザのメモリ上にあるだけです。ページをリロードすると、アップロードしたファイルは全部消えて初期状態に戻ります。Day 3 のテストで「前提条件」「事後処理」を書くのは、この性質を利用（あるいは回避）するためです。

🏭Clean Architecture ＝ 厨房の持ち場

ちゃんとした厨房は、場所ごとに役割が決まっています。仕込み場、コンロ前、盛り付け台。盛り付け担当が勝手に食材を仕入れに行かないから、混乱せずに回ります。

食材の仕入れ口→src/adapters/ — 外部（API・ストレージ）とのやりとり専門
レシピと調理知識→src/domain/ — 業務ルールと型定義。外部に一切依存しない
店全体の段取り→src/app/ — ルーティングや全体設定
盛り付け・配膳→src/presentations/ — 画面に見えるもの全部

この線引きがあると、「サーバーを本物に差し替える」ときに adapters/ だけ直せば済みます。画面のコードは触らなくていい。

SECTION 03重要なコード

1. 環境をチームで揃える — .npmrc

環境構築でいちばん最初に効いてきたファイルです。たった3行ですが、これのおかげで Node.js を手動インストールせずに済みました。

.npmrc 
# engine-strict: package.json の engines 指定と違う Node で動かそうとしたらエラーで止める
#                「バージョン違うけど動くやろ」を許さない設定
engine-strict=true

# use-node-version: pnpm がこのバージョンの Node.js を自動でダウンロードして使う
#                   → 自分のPCに Node が入っていなくてもいい。pnpm さえあれば揃う
use-node-version=22.23.1

# package-manager-strict: package.json の packageManager と違う pnpm だとエラー
#                         今回は pnpm@10.12.4 ちょうどが必要だった理由がこれ
package-manager-strict=true
なぜ大事か

「自分のPCでは動くのに、他の人の環境では動かない」の最大の原因がバージョン違いです。この3行が、全員を強制的に同じ環境に揃えます。

2. タスク分解の読み方 — tasks.md

/speckit.tasks が吐き出す1行1行には、決まった意味があります。

specs/002-document-management-example/tasks.md 
## Format: [ID] [P?] [Story] Description

// [x] = 完了済み / T001 = タスク番号（実装はこの番号を指定して呼び出す）
- [x] T001 依存パッケージのインストール `pnpm add @mui/x-data-grid react-dropzone date-fns`

// [P] = Parallel。他のタスクとファイルが被らないので"同時に進めてよい"印
- [x] T002 [P] OpenAPI仕様を `schema/files/openapi.yaml` にコピー

// [US1] = User Story 1 に属するタスク。仕様書のどの機能のためかを紐づけている
//        → 「Story 1 だけ完成させて動作確認」という進め方ができる
- [x] T044 [P] [US1] FileUploadZoneコンポーネント `.../FileUploadZone.tsx`

// 説明には必ず"正確なファイルパス"が入る。AIが迷わず書き込めるようにするため
- [x] T049 [P] [US2] FileListTableコンポーネント（MUI DataGrid使用） `.../FileListTable.tsx`

フェーズの順番にも意味があります。Phase 1（セットアップ）→ Phase 2（基盤）→ Phase 3以降（機能ごと）。Phase 2 が終わるまで機能の実装に入れないのは、土台がないと全部やり直しになるからです。

3. 一覧テーブルの定義 — FileListTable.tsx

Day 2 の成果物の中核。MUI の DataGrid に「どんな列を出すか」を渡している部分です。

src/presentations/pages/FilesPage/components/MyFilesSection/components/FileListTable/FileListTable.tsx 
const columns: GridColDef<DocumentFile>[] = React.useMemo(
  () => [
    {
      field: 'name',          // データのどのプロパティを表示するか（file.name）
      headerName: 'Name',      // 列見出しに出る文字。E2Eテストではこれをクリックしてソートする
      flex: 1,                  // 余った横幅を他の列と等分する
      minWidth: 300,           // これ以上は縮まない下限
      renderCell: (params) => (  // セルの見た目を自作する。ここではアイコン＋ファイル名
        <DataGridCellContent>
          <Avatar><DescriptionIcon /></Avatar>
          <Typography variant="body2" noWrap>{params.value}</Typography>
        </DataGridCellContent>
      ),
    },
    {
      field: 'uploadedAt',
      headerName: 'Last Modified',
      // valueFormatter: 中身の値だけ変換する（見た目は DataGrid 標準のまま）
      // サーバーから来る日時データを "2026/08/25 10:30" の形に整える
      valueFormatter: (value) => format(value, 'yyyy/MM/dd HH:mm'),
    },
    {
      field: 'size',
      headerName: 'File Size',
      // バイト数（1048576）を "1.0 MB" のような人が読める形に変換
      valueFormatter: (value) => formatFileSize(value),
    },
  ],
  [getFileTags]  // この値が変わったときだけ columns を作り直す（毎回作ると遅い）
);
renderCell と valueFormatter の使い分け

renderCell は「セルの中身を HTML ごと差し替える」。valueFormatter は「文字列だけ整形する」。日付やサイズのようなただの変換なら valueFormatter のほうが軽くて速いです。

4. 検索状態を URL に持たせる — useFilesSearchParams.ts

地味ですが、設計として一番おもしろい部分です。検索キーワードを React の state ではなく URL のクエリパラメータに保存しています。

src/presentations/pages/FilesPage/hooks/useFilesSearchParams.ts 
export function useFilesSearchParams() {
  // React Router の機能。URL の ?search=... の部分を読み書きする
  const [searchParams, setSearchParams] = useSearchParams();

  const setSearchQuery = useCallback(
    (query: string) => {
      if (query) {
        // URL に ?search=田中商事 を書き込む
        searchParams.set(QUERY_PARAMS.SEARCH, query);

        // ★重要★ 検索したらページ番号を消す＝1ページ目に戻す
        // これがないと「5ページ目を見ている状態で検索 → 結果2件なのに5ページ目」
        //                → 何も表示されない、というバグになる
        searchParams.delete(QUERY_PARAMS.PAGE);
      } else {
        // キーワードが空なら ?search= ごと消す（URLを汚さない）
        searchParams.delete(QUERY_PARAMS.SEARCH);
      }

      // replace: true = ブラウザの履歴を積み上げない
      // 1文字打つたびに履歴が増えると、戻るボタンが使い物にならなくなる
      setSearchParams(searchParams, { replace: true });
    },
    [searchParams, setSearchParams]
  );

  return { searchQuery: getSearchQuery(), page: getPage(), /* ... */ setSearchQuery };
}
URL に状態を持たせる利点

検索結果の URL をそのまま同僚に送れる。ブラウザの「戻る」が期待どおり動く。リロードしても検索条件が消えない。React の state に入れていたら、この3つが全部できません。

5. 検索中は画面を切り替える — FilesPage.tsx

ページ本体は驚くほど短い。「組み立てるだけ」に徹しているのが Clean Architecture の効果です。

src/presentations/pages/FilesPage/FilesPage.tsx 
export const FilesPage: React.FC = () => {
  // URL から検索キーワードとタグを取り出す（上のフックを使用）
  const { searchQuery, tagIds } = useFilesSearchParams();

  // !! で「文字列 → 真偽値」に変換。キーワードがあれば true
  const isSearching = !!searchQuery;

  return (
    // data-testid: E2Eテストがこの画面を見つけるための目印（憲法で必須）
    <S.Page data-testid="filesPage">
      {!isSearching && (
        // 検索中でないときだけ「最近使ったファイル」と「アップロード欄」を出す
        // → 検索中は結果に集中させる、という UX 上の判断
        <>
          <RecentFilesSection />
          <UploadSection />
        </>
      )}
      // 一覧は常に表示。検索条件を渡して中で絞り込ませる
      <MyFilesSection searchQuery={searchQuery} tagIds={tagIds} />
    </S.Page>
  );
};

SECTION 04今回の学び

つまずきWSL が Windows の Node.js を拾っていた

corepack enable が /bin/sh^M: 誤ったインタプリタです というエラーで落ちました。原因は、WSL（Linux）が Windows 側にインストールされた Node.js を見に行っていたこと。Windows のファイルは改行コードが CRLF で、Linux はそれを ^M という余計な文字として読んでしまいます。

教訓：WSL で開発するときは、ツールも WSL の中に入れる。which pnpm の結果が /mnt/c/... だったら Windows 側を見ている合図です。

気づき環境構築は「pnpm を入れるだけ」で済んだ

.npmrc の use-node-version のおかげで、Node.js を自分でインストールする必要がありませんでした。pnpm がプロジェクト指定のバージョンを勝手にダウンロードしてくれます。

教訓：環境構築で詰まったら、まず設定ファイル（.npmrc / package.json の engines・packageManager）を読む。手順書より設定ファイルのほうが正確です。

つまずき<your-name> をそのまま貼ってエラー

手順書の git checkout -b 002-document-management-<your-name> をそのままコピペしたら「予期しないトークン」エラー。bash は < を「ファイルから入力を読み込め」という命令として解釈するためです。

教訓：手順書の < > や [ ] で囲まれた部分は「ここを自分の値に置き換えて」の意味。記号ごと消して置き換えます。

気づき仕様書と実装は、けっこうズレる

実際に動かして初めて分かった食い違いがいくつもありました。

  • 仕様（FR-010）は「1ページ20件」→ 実装は10件
  • 資料の画面URLは /files → 実装は /（ルート）
  • 仕様（FR-016）は「ファイル名とタグ名で検索」→ 実装はタグ名では検索できない
  • グリッドビュー切替・検索ハイライトは未実装

教訓：仕様書は「そうあってほしい姿」であって、動いているコードの説明書ではありません。テストを書くときは必ず実物を触って確かめる。ドキュメントを信じて書いたテストは落ちます。

気づきタスクに [P] と [US1] がついている理由

[P] は「他とファイルが被らないので並行してよい」、[US1] は「User Story 1 のためのタスク」。この2つの印があるおかげで、Story 1 だけ先に完成させて動作確認するという進め方ができます。

教訓：130 個のタスクを上から順にやる必要はない。優先度 P1 のストーリー単位で「動く状態」を作りながら進めるほうが、途中で時間切れになっても成果が残ります。

つまずきMSW のデータはリロードで消える

アップロードしたファイルはブラウザのメモリにしかありません。リロードすると初期状態（0件）に戻ります。

教訓：これは欠点ではなくテストにとっては長所。テストごとにリロードすれば、毎回まっさらな状態から始められます。Day 3 で「事後処理：リロードしてリセット」と書くのはこのためです。

気づき生成されたコードは手で直さない

src/adapters/generated/ の中身は pnpm gen:api が作ったもの。手で編集しても、次にコマンドを打った瞬間に上書きされて消えます。

教訓：直すべきは元になった設計図（schema/files/openapi.yaml）のほう。「自動生成されたファイルは触らない」はどのプロジェクトでも共通のルールです。

気づきAI に任せる部分と、人が決める部分

Spec Kit は構造とコードを生成しますが、「何を作るか」「どの機能を優先するか」は人が決める。実際、P1 の3ストーリーに絞る判断も、仕様と実装のズレをどう扱うかの判断も、AI ではなく自分がやりました。

教訓：Day 0 の資料にあった「AI支援、人間主導」はスローガンではなく、実際の作業配分そのものでした。
